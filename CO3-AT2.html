Servlet Architecture & Workflow

Java Servlet architecture follows a client-server model. A client such as a web browser sends an HTTP request to the web server. The web container receives the request, identifies the appropriate servlet and manages its execution.

Complete Request–Response Cycle

Client Browser | | 1. HTTP Request ↓ Web Server | | 2. Forward Request ↓ Web Container | | 3. Locate Servlet ↓ Servlet | | 4. Process Request | | 5. Business Logic / Database | | 6. Generate Response ↓ Web Container | | 7. HTTP Response ↓ Client Browser

🌐 Client

Sends HTTP requests through a browser and displays the response.

⚙️ Web Container

Manages servlet creation, execution, threads, requests and responses.

📥 Request Object

Contains form data, parameters, headers and request information.

📤 Response Object

Used by the servlet to send HTML, JSON or other responses to the client.

Request and Response Example

protected void doGet(HttpServletRequest request,
                      HttpServletResponse response)
                      throws IOException {

    String name = request.getParameter("name");

    response.setContentType("text/html");

    PrintWriter out = response.getWriter();

    out.println("<h1>Welcome " + name + "</h1>");
}

Servlet Life Cycle Analysis

The Servlet Life Cycle is controlled by the web container. It consists mainly of initialization, request processing and destruction.

Life Cycle Sequence

Web Container | ↓ Create Servlet Object | ↓ init() | ↓ service() | ┌─────┴─────┐ ↓ ↓ doGet() doPost() │ │ └─────┬─────┘ ↓ Process Requests | ↓ destroy()

1️⃣ init()

Called only once when the servlet is initialized. It is used for initialization tasks.

2️⃣ service()

Called for every client request and dispatches the request to doGet(), doPost(), etc.

3️⃣ destroy()

Called once before the servlet is removed. Used to release resources.

Life Cycle Methods

public void init() throws ServletException {

    // Initialization
    System.out.println("Servlet Started");
}


protected void service(HttpServletRequest request,
                       HttpServletResponse response)
                       throws ServletException, IOException {

    // Request processing
}


public void destroy() {

    // Release resources
    System.out.println("Servlet Destroyed");
}
⚡ Performance Implications
  • init() executes once, so expensive initialization can be performed here.
  • service() executes repeatedly, so request processing should be efficient.
  • Database connections and other resources should be managed carefully.
  • The container uses threads to process multiple requests efficiently.
  • destroy() should release resources to prevent resource leaks.
Life Cycle: Loading → Instantiation → init() → service() → destroy()

GET vs POST Method Evaluation

GET and POST are HTTP methods used to communicate between the client and server and to submit form data.

Feature GET POST
Data Transmission URL / Query String HTTP Request Body
Visibility Visible in URL Not normally visible in URL
URL Limitation Limited by URL length Suitable for larger data
Bookmarking Can be bookmarked Normally not bookmarked as submitted data
Typical Purpose Retrieve data Submit/change data
Sensitive Data Not recommended More appropriate with HTTPS

GET Example

<form action="StudentServlet" method="get">

    <input type="text" name="name">

    <input type="submit" value="Search">

</form>
Example URL:

StudentServlet?name=Student

POST Example

<form action="StudentServlet" method="post">

    <input type="text" name="name">

    <input type="email" name="email">

    <input type="submit" value="Register">

</form>

🔎 GET

Best for search, filtering and retrieving information.

📤 POST

Best for registration, login, uploading and creating records.

Security: POST does not encrypt information by itself. Sensitive information should always be transmitted using HTTPS.

Session Tracking Techniques

HTTP is stateless. Session tracking mechanisms allow web applications to identify the same user across multiple requests.

Three Main Techniques

🔐
HttpSession
🍪
Cookies
🔗
URL Rewriting

1. HttpSession

HttpSession session =
    request.getSession();

session.setAttribute(
    "username",
    "Student"
);

Advantages

  • Data is maintained on the server.
  • Suitable for authentication.
  • Can store multiple attributes.
  • Useful for shopping carts.

2. Cookies

Cookie cookie =
    new Cookie("username", "Student");

response.addCookie(cookie);

Advantages and Limitations

  • Stored in the browser.
  • Easy to implement.
  • Useful for preferences.
  • Limited storage size.
  • Users can delete or disable cookies.

3. URL Rewriting

String url =
    response.encodeURL("home.jsp");
Example:

home.jsp;jsessionid=ABC123
Technique Storage Advantages Limitations Use Case
HttpSession Server Good for authentication Uses server resources Login / Cart
Cookies Client Simple and persistent Limited and client-controlled Preferences
URL Rewriting URL Works without cookies Session ID visible in URL Cookie-disabled clients

Cookies vs Sessions – Critical Analysis

Cookies and sessions are both used for maintaining state in web applications, but they differ in where information is stored and how it is managed.

Cookie and Session Relationship

┌───────────────────────┐ │ Browser │ │ │ │ Cookie │ │ JSESSIONID=XYZ │ └───────────┬───────────┘ │ │ Session ID ↓ ┌───────────────────────┐ │ Server │ │ │ │ HttpSession │ │ │ │ Username │ │ Shopping Cart │ │ Login State │ └───────────────────────┘
Feature Cookies Sessions
Storage Location Client / Browser Server
Data Size Small Generally larger
Security More exposed to client-side risks Application data remains server-side
Lifetime Can be persistent Usually timeout-based
User Control User can modify/delete Server manages session data
Performance Adds data to requests Uses server-side resources
Common Use Preferences Authentication / Cart

Real-Time Use Cases

🛒 E-Commerce

Sessions can maintain a user's shopping cart while cookies can remember preferences.

🏦 Online Banking

A server-side session can maintain the authenticated user's login state.

🎬 Streaming

Cookies can remember preferences while sessions maintain authenticated access.

🌐 Websites

Cookies can store language, theme and other non-sensitive preferences.

Security Best Practices

  • Always use HTTPS for sensitive communication.
  • Use HttpOnly cookies when appropriate to reduce JavaScript access to session cookies.
  • Use the Secure cookie attribute so cookies are sent only over HTTPS.
  • Use an appropriate SameSite setting.
  • Expire sessions after an appropriate period.
  • Invalidate sessions during logout.
  • Regenerate session identifiers after authentication where appropriate.
Final Analysis: Sessions are generally more suitable for sensitive server-managed application state such as login information and shopping carts. Cookies are more suitable for small, non-sensitive client-side information such as preferences.
