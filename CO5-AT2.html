1. REST vs SOAP Web Service Design

A company needs to develop a web service for both mobile and web applications. REST and SOAP are two common approaches for implementing web services.

REST and SOAP Comparison

Feature REST SOAP
Data Format Usually JSON XML
Performance Fast and lightweight More processing overhead
Scalability Highly scalable Suitable for enterprise applications
Security HTTPS, OAuth, JWT HTTPS, WS-Security
Mobile Support Excellent More complex
Communication HTTP methods SOAP messages

Selected Approach: REST

REST is selected because the application must support mobile and web clients. REST APIs are lightweight, easy to implement, use JSON efficiently, provide good performance, and can scale horizontally.

REST Architecture

Mobile App
→
REST API
→
Application Server
→
Database

Example Request

GET /api/products/101

Authorization: Bearer JWT_TOKEN
Accept: application/json

Example Response

{
    "id": 101,
    "name": "Laptop",
    "price": 55000,
    "available": true
}

Justification

Performance

REST usually uses lightweight JSON data, reducing communication overhead.

Scalability

REST services are stateless, making it easier to distribute requests across multiple servers.

Security

HTTPS, authentication tokens, OAuth and authorization mechanisms can secure REST APIs.

3. Secure Communication for Banking Application

A banking application handles sensitive information such as account numbers, passwords and transaction details. Therefore, communication between client and server must be strongly protected.

Protocol Analysis

Protocol Security Reliability Suitable For Banking?
HTTP Low Good No
HTTPS High High Yes
FTP Low Good No
SSH Very High High Not normally for user web traffic

Selected Protocol: HTTPS

HTTPS is selected because it uses TLS to encrypt communication between the client and server. It provides confidentiality, integrity protection and server authentication through certificates.

Banking Communication Flow

Banking App
→
HTTPS / TLS
→
Bank Server
→
Secure DB

Security Mechanisms

Encryption

TLS encrypts sensitive information during transmission.

Authentication

User authentication and multi-factor authentication can prevent unauthorized access.

Integrity

TLS provides protection against unauthorized modification of transmitted information.

Communication Process

1. Client opens an HTTPS connection.

2. TLS handshake is performed.

3. Server certificate is verified.

4. Secure session keys are established.

5. Client sends encrypted request.

6. Server processes the request.

7. Server sends encrypted response.

8. Client displays the result.
HTTPS provides an appropriate balance of security, reliability and performance for banking applications. Additional controls such as MFA, authorization, secure session management and transaction monitoring should also be implemented.

4. Third-Party API Integration Strategy

Applications often integrate external services such as payment gateways, map services, SMS services and authentication providers.

API Integration Flow

Application
→
API Gateway
→
Authentication
→
Third-Party API
→
Response

Step 1: Create Request

POST /payment

Content-Type: application/json

{
    "amount": 5000,
    "currency": "INR",
    "orderId": "ORD101"
}

Step 2: Authentication

The application authenticates with the third-party service using a secure mechanism such as an API key, OAuth token or signed request. 

Authorization: Bearer ACCESS_TOKEN

Step 3: Send Request

The request is transmitted using HTTPS. The API gateway can validate authentication, rate limits and request format before forwarding the request.

Step 4: Receive Response

{
    "status": "success",
    "transactionId": "TXN4567",
    "amount": 5000
}

Step 5: Process Response

  • Check HTTP status code.
  • Validate response format.
  • Verify transaction information.
  • Update the application's database.
  • Display the result to the user.

Error Handling

IF status = 200
    Process successful response

ELSE IF status = 401
    Re-authenticate or refresh token

ELSE IF status = 429
    Wait and retry

ELSE IF status >= 500
    Retry using backoff

ELSE
    Display appropriate error
END IF

Alternative Approach: API Gateway

An API Gateway provides a centralized layer between the application and external services. It can provide authentication, rate limiting, caching, routing, monitoring and centralized error handling.

Security

5. Error Handling and Fault Tolerance

A web service may encounter invalid requests, authentication failures, network problems, server errors or excessive traffic. A fault-tolerant design ensures that these errors do not bring down the entire system.

Common Web Service Errors

Error Meaning Action
400 Bad Request Validate user input
401 Unauthorized Authenticate user
403 Forbidden Check permissions
404 Not Found Check requested resource
429 Too Many Requests Use rate limiting and retry
500 Internal Server Error Log and recover

Error Handling Flow

Client Request
→
Validate
→
Authenticate
→
Process
→
Response

Fault-Tolerance Mechanisms

Retry

Temporarily failed requests can be retried after a controlled delay.

Timeout

Prevents a client from waiting indefinitely for an unavailable service.

Circuit Breaker

Stops repeated requests to an unhealthy service and allows the system to recover.

Fallback

Provides an alternative response or service when the primary service fails.

Error Handling Algorithm

START

1. Receive client request.

2. Validate request.

3. IF request is invalid THEN
       Return HTTP 400.
       Display appropriate error.
       STOP.
   END IF

4. Authenticate the client.

5. IF authentication fails THEN
       Return HTTP 401.
       STOP.
   END IF

6. Process the request.

7. IF temporary network/server error occurs THEN
       Retry with exponential backoff.
   END IF

8. IF service continues to fail THEN
       Activate circuit breaker.
   END IF

9. Use fallback service if available.

10. Log the error.

11. Monitor system health.

12. Return appropriate response.

END
