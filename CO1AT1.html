Section 01

Embedding the promotional video

Requirement: the homepage needs a promotional video, playable without a third-party plugin.

▲ live demo — 10-second promo clip, plays automatically and loops (unmute using the controls)

Snippet 1 · Video embedding options

  • A. <media src="video.mp4"></media>
  • B. <video src="video.mp4" controls></video>
  • C. <movie src="video.mp4"></movie>
  • D. <vid src="video.mp4"></vid>

Q1 · Select the correct HTML tag for video embedding and justify your answer.

Answer: B — <video>. It's the only element in the list that is part of the actual HTML5 specification; browsers ship built-in decoding and playback controls for it, so no plugin or external library is needed. <media>, <movie>, and <vid> (options A, C, D) are not real HTML elements — a browser doesn't recognize them, so it renders them as plain inline text with no player at all.

<!-- native HTML5 video, no plugin dependency -->
<video controls autoplay muted loop playsinline>
  <source src="promo.mp4" type="video/mp4">
  <p>Your browser doesn't support HTML video.</p>
</video>

Why this shape: the <video> element ships natively in every modern browser, so no Flash or external embed is needed. Browsers only allow autoplay when the video is also muted, so that attribute pairs with it here; controls still lets a visitor unmute or pause, and loop keeps a short promo clip like this one running continuously.

Section 02

Sending registration data securely

Requirement: the registration form must send user data to the server without exposing it in the URL or browser history.

🔒 submitted over HTTPS via POST — never appears in the URL

Snippet 2 · Form submission methods

  • A. GET
  • B. POST
  • C. PUT
  • D. DELETE

Q2 · Identify the appropriate HTTP method for form submission and explain why.

Answer: B — POST. POST sends the form fields in the request body rather than the URL, which keeps sensitive data like passwords out of the address bar, browser history, and server access logs. GET (A) exposes data as a visible query string, which is fine for a search box but wrong for a registration form. PUT (C) and DELETE (D) are REST methods meant for updating or removing an existing resource at a known URL — a new registration is a resource being created, and browser <form> elements don't natively support PUT/DELETE anyway.

<form action="/api/register" method="post">
  <input type="email" name="email" required>
  <input type="password" name="password" required>
  <button type="submit">Create account</button>
</form>

Why POST, not GET: GET appends form fields to the URL as a query string, so a password would sit in plain text in the browser's address bar, history, and any server access logs. POST sends the data in the request body instead. That alone doesn't encrypt it in transit — the encryption comes from serving the page over HTTPS (see Section 05), which wraps the whole request, body included, in TLS.

Section 03

A semantic navigation menu

Requirement: the navigation menu must use semantic HTML rather than generic containers, so screen readers and search engines can identify it as navigation.

Before — div soup <div class="menu"> <div class="menu-item"><a href="/">Home</a></div> <div class="menu-item"><a href="/pricing">Pricing</a></div> </div>
After — semantic markup <nav aria-label="Primary"> <ul> <li><a href="/">Home</a></li> <li><a href="/pricing">Pricing</a></li> </ul> </nav>

Snippet 3 · Navigation elements

  • A. <div>
  • B. <nav>
  • C. <section>
  • D. <header>

Q3 · Choose the proper semantic element for navigation and justify its usage.

Answer: B — <nav>. It's the element the HTML spec defines specifically for a block of navigation links, so screen readers expose it as a "navigation" landmark users can jump straight to, and search engines use it to map site structure. <div> (A) is a generic box with no meaning at all. <section> (C) marks a generic thematic grouping of content, not specifically links. <header> (D) marks introductory content for a page or section — a nav menu is often placed inside a header, but the header element itself doesn't say "these are navigation links."

Why it matters: a <div> carries no meaning — assistive technology has no way to know it's navigation. <nav> is announced by screen readers as a navigation landmark, letting users jump straight to it, and search engines use it to understand site structure. The live menu at the top of this page (01 · Video …) is built exactly this way — inspect it to see the real markup.

Section 04

Fixing the XML configuration file

Requirement: the app's XML config files must be well-formed — one unclosed or mismatched tag stops the parser cold.

Before — three syntax errors <?xml version="1.0"?> <config> <database> <host>localhost<host> <!-- 1: closing tag should be </host> --> <port>5432</port> <!-- 2: missing ">" after <port --> </database> <Timeout>30</timeout> <!-- 3: tag names are case-sensitive --> <config> <!-- 4: missing "/" — root never closes -->
After — well-formed <?xml version="1.0" encoding="UTF-8"?> <config> <database> <host>localhost</host> <port>5432</port> </database> <timeout>30</timeout> </config>

Snippet 4 · XML syntax

  • A. <note><to>User</to><from>Admin</from>
  • B. <note><to>User</to><from>Admin</from></note>
  • C. <note><to>User</from></note>
  • D. <note to="User"></note

Q4 · Identify the correct XML syntax and explain the error in other options.

Answer: B. Every element opened is closed with a matching tag (<to>…</to>, <from>…</from>), and all of it nests inside one root element, <note>…</note>. Option A never closes the root <note> element, so the document has no defined end. Option C opens a <to> tag but closes it with </from> — a mismatched closing tag, which XML parsers reject outright. Option D is missing the closing
