TICKET-01 · HTTP

HTTP Response Header Analysis

1HTTP/1.1 200 OK
2Date: Mon, 01 Apr 2026 10:00:00 GMT
3Content-Type: text/html
4Content-Length: -150
5Connection: keep-alive
1 · invalid fields

Line 4 is the fault: Content-Length: -150. Per RFC 9110, Content-Length must be a non‑negative decimal integer representing the exact byte size of the message body — a negative value is not a legal representation at all, so a strict parser should treat it as a protocol error rather than a byte count. Everything else in the header block is syntactically valid: the status line, Date, Content-Type, and Connection are all well-formed.

2 · impact of the negative length

Content-Length tells the client exactly how many bytes to read before considering the body complete. A negative number breaks that contract in a few concrete ways:

  • Parsing failure — most HTTP clients and proxies will reject the response outright or fall back to reading until the connection closes.
  • Connection reuse breaks — with keep-alive active, the client relies on Content-Length to know where this response ends and the next one begins. An invalid value makes the boundary undecidable, risking a "request smuggling"-style desync on the same TCP connection.
  • Security surface — malformed length fields are a known vector for HTTP request/response smuggling when front-end and back-end servers disagree on how to interpret the value.
3 · does the status code match?

200 OK asserts the request succeeded and a valid body is attached — but a response can't simultaneously claim success and carry a header that makes the body unreadable. The status code itself is a legitimate code, it just doesn't match a response whose framing is broken; a well-behaved server would never emit this combination.

corrected header
1HTTP/1.1 200 OK
2Date: Mon, 01 Apr 2026 10:00:00 GMT
3Content-Type: text/html
4Content-Length: 150
5Connection: keep-alive

Set Content-Length to the actual byte count of the body (e.g. via strlen() / buffer size on the server), and if that value is ever unreliable, switch to Transfer-Encoding: chunked instead of guessing.

TICKET-02 · DOM

DOM Structure Analysis

1<html>
2  <head>
3    <title>Test Page</title>
4  </head>
5  <body>
6    <div>
7      <p>Hello World
8    </div>
9  </body>
10</html>
1 · missing / improperly closed elements

The <p> opened on line 7 is never explicitly closed with </p> before the </div> on line 8. That's the only structural defect here — the <div>, <body>, <html>, and <head> all close correctly.

2 · how the browser interprets it

This is where HTML's error-recovery rules matter: <p> is on the HTML5 list of tags that auto-close when certain other tags are encountered. When the parser hits the closing </div> tag, it treats that as an implicit signal to close the still-open <p> first. So the browser silently rewrites the tree to:

<div>
  <p>Hello World</p>
</div>

No parse error is thrown, and the page renders visually the same as if the tag had been closed correctly.

3 · impact on rendering and layout

In this exact case, impact is minimal — the DOM self-corrects and layout looks right. But the pattern is risky in general:

  • If a different element (like another <p> or a <span>) came between the open <p> and the </div>, the auto-close rule can produce a nesting the author never intended.
  • CSS selectors and JS DOM traversal (querySelector, childNodes) operate on the corrected tree, not the source markup, so debugging becomes confusing if you're reading raw HTML instead of the inspected DOM.
  • Relying on auto-closing is non-portable: XML-based tooling (XHTML, some templating engines, RSS/Atom generators) has no such recovery and will hard-fail on the same markup.
corrected markup
<html>
  <head>
    <title>Test Page</title>
  </head>
  <body>
    <div>
      <p>Hello World</p>
    </div>
  </body>
</html>

TICKET-03 · Security

GET vs POST in a Login System

MethodURL exampleData locationRisk
GET/login?user=admin&pass=1234Query string (URL)High
POST/loginRequest bodyLower, not zero
1 · how data transmission differs

GET appends form data as a query string directly on the URL, which means it travels wherever the URL travels. POST places the same data inside the request body, separate from the URL, and typically pairs it with Content-Type: application/x-www-form-urlencoded or multipart/form-data.

2 · which method suits login

POST is the correct choice. Beyond keeping credentials out of the URL, GET requests are semantically defined as idempotent and "safe" — meant for retrieving data, not causing state changes like authenticating a session. Browsers, proxies, and CDNs are also allowed to cache GET requests, which is exactly the wrong behavior for a password submission.

3 · security risks of GET for auth
  • Browser history — the full URL, password included, is saved locally and persists after logout.
  • Server & proxy logs — most web servers log the request line by default, so credentials land in plaintext log files.
  • Referer header leakage — if the login page links out afterward, the URL (with credentials) can be sent to a third-party site via the Referer header.
  • Shoulder-surfing / screen-sharing — visible in the address bar during demos, screenshots, or screen shares.
  • Caching — intermediate caches may store the response keyed to a URL that contains the password.
4 · best practices for secure login
  • Always submit credentials via POST, over HTTPS/TLS — POST alone doesn't encrypt anything; without TLS the body is just as visible on the wire.
  • Never place tokens or passwords in the URL, including in redirects.
  • Hash and salt passwords server-side (e.g. bcrypt/argon2); never store or log plaintext.
  • Set Cache-Control: no-store on auth responses so intermediaries don't cache them.
  • Use secure, HttpOnly, SameSite cookies for session tokens after login.
  • Rate-limit and add CSRF protection to the login endpoint.
